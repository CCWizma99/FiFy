Fashion RAG System — Detailed Architecture Specification

1. System Overview
The system is a multimodal fashion search engine that accepts image uploads or text descriptions from users and returns visually and semantically similar fashion items scraped from selected retail websites. The core innovation is twofold — an AI-driven dynamic scraping agent that adapts to website structures, and a vector-based image matching system that stores embeddings rather than raw images.
The system is composed of five major components: the Scraping and Ingestion Pipeline, the Embedding Engine, the Vector Database, the Search and Retrieval Backend, and the Frontend Interface.

2. Target Sites for MVP
Start with these five sites as they cover a good range of fashion categories and have relatively consistent HTML structures:

ASOS
Zara
H&M
Uniqlo
Zalando

Each site gets its own scraping configuration generated by the AI agent and cached for reuse.

3. Scraping and Ingestion Pipeline
This is the background pipeline that runs on a schedule and populates your vector database. It never runs in real time during user interactions.
3.1 Site Analyzer Agent
When a new site is introduced to the system, the Site Analyzer Agent is triggered. It uses an LLM (Google Gemini via API) to inspect the raw HTML of a product listing page and a product detail page. The LLM is prompted to identify the CSS selectors or XPath patterns for the following fields:

Product name
Price
Product image URL
Product category
Product detail page URL
Brand name (if available)

The LLM returns a structured JSON scraping configuration like this:
json{
  "site": "asos.com",
  "listing_url_pattern": "https://www.asos.com/women/dresses/cat/?cid=8799",
  "pagination_selector": "a[data-auto-id='loadMoreProducts']",
  "product_card_selector": "article[data-auto-id='productTile']",
  "fields": {
    "name": "div[data-auto-id='productTile-description']",
    "price": "span[data-auto-id='productTile-price']",
    "image_url": "img.productTile-image",
    "product_url": "a.productTile-link"
  }
}
This configuration is saved to a configs directory and reused on every subsequent scrape of that site. The LLM is only called again if the scraper starts returning empty fields, which indicates the site has updated its structure.
3.2 Scraper Executor
Built with Playwright for JavaScript-heavy sites. For each target site it loads the scraping configuration, navigates through paginated listing pages, extracts raw product data, and passes each product to the embedding pipeline. The image is downloaded temporarily into memory — never written to disk.
The scraper runs on a configurable schedule, recommended every 48 hours for MVP. It also maintains a URL hash registry so it skips products it has already processed unless the price has changed.
3.3 Data Validation Layer
Before any product reaches the embedding engine it passes through a lightweight validation check:

Image URL must return a 200 status
Product name must not be empty
Price must be parseable as a number
Product URL must resolve to the correct domain

Failed products are logged to a dead letter queue for review. They are not discarded immediately — a retry is attempted once after 24 hours before permanent removal.

4. Embedding Engine
This is the heart of the system technically. It converts both scraped product images and user queries into vectors that can be compared mathematically.
4.1 Model Choice
Use OpenAI's CLIP model (specifically ViT-B/32 as a starting point) via the HuggingFace transformers library. CLIP is ideal here because it was trained on image-text pairs, meaning image vectors and text vectors exist in the same semantic space. This is what allows a text description like "red floral summer dress" to match against image vectors of actual red floral dresses.
4.2 Image Embedding Flow
Product image URL
      ↓
Download image into memory (PIL / io.BytesIO)
      ↓
Preprocess (resize to 224x224, normalize)
      ↓
Pass through CLIP image encoder
      ↓
Output: 512-dimensional float vector
      ↓
Discard image from memory
      ↓
Store vector in Qdrant
4.3 Text Embedding Flow
For the product name and category, generate a separate text embedding using the CLIP text encoder. Store both the image vector and the text vector for each product. During search you can weight them or search against both.
4.4 User Query Embedding
When a user uploads a photo, it goes through the exact same image embedding flow as above. When a user types a description, it goes through the text embedding flow. The resulting vector is then used directly as the search query against Qdrant. No separate query transformation is needed — this is the elegance of CLIP.

5. Vector Database
5.1 Database Choice
Use Qdrant. It has a generous free cloud tier, excellent Python SDK, supports named vectors (so you can store both image and text vectors per product in the same point), and has built-in filtering which you will need for category and price range filtering.
5.2 Collection Schema
Each product is stored as a single point in Qdrant with the following structure:
json{
  "id": "uuid-generated-at-ingestion",
  "vectors": {
    "image": [0.023, -0.147, ...],
    "text": [0.081, 0.203, ...]
  },
  "payload": {
    "product_name": "Floral Midi Dress",
    "brand": "ASOS Design",
    "price": 45.99,
    "currency": "USD",
    "category": "dresses",
    "gender": "women",
    "product_url": "https://asos.com/...",
    "image_url": "https://images.asos-media.com/...",
    "source_site": "asos.com",
    "scraped_at": "2025-04-27T10:00:00Z",
    "is_active": true
  }
}
5.3 Search Strategy
For image upload queries, search against the image vector with a cosine similarity metric. For text description queries, search against the text vector. Return the top 20 results by default, which the frontend displays as a grid.
Qdrant filters can be applied at search time for things like price range, category, or gender without needing a separate filtering step.

6. Backend API
Built with FastAPI in Python. This is the layer your frontend talks to and the layer that orchestrates the scraping jobs.
6.1 Endpoints
POST   /search/image        — accepts image upload, returns matched products
POST   /search/text         — accepts text query, returns matched products
GET    /products/{id}       — returns single product metadata
POST   /admin/scrape/trigger — manually trigger a scrape job (admin only)
GET    /admin/scrape/status  — check scraping job status
GET    /health               — basic health check
6.2 Search Endpoint Logic (Image)
Receive image file
      ↓
Validate (size < 5MB, must be jpg/png/webp)
      ↓
Generate CLIP image embedding
      ↓
Query Qdrant with vector + any filters from request
      ↓
Get top 20 results with payloads
      ↓
Validate image URLs are still alive (async, non-blocking)
      ↓
Return product list as JSON
6.3 Search Endpoint Logic (Text)
Receive text string
      ↓
Validate (not empty, max 200 chars)
      ↓
Generate CLIP text embedding
      ↓
Query Qdrant with vector
      ↓
Return product list as JSON
6.4 Background Jobs
Use APScheduler within FastAPI to run scraping jobs on a cron schedule. Each site runs as an independent job so a failure on one site does not affect others. Job status is tracked in a simple SQLite table for MVP — no need for Redis or Celery at this stage.

7. Frontend Interface
Keep this simple for MVP. The goal is a clean, functional demo.
7.1 Core Pages
Single page application with three states:
Home/Search State — A clean centered layout with two input options. A drag-and-drop image upload zone and a text input field below it. A search button. Nothing else on the page to distract.
Results State — A product grid (3-4 columns on desktop, 2 on mobile) showing product cards. Each card shows the live product image loaded from the retailer URL, product name, brand, price, source site badge, and a "View Item" button linking to the retailer.
Loading State — A simple skeleton loader while the search is processing. Expected wait time is 1-3 seconds.
7.2 Tech Choice
React with TailwindCSS is the recommended choice given its simplicity and how quickly you can build a clean UI. If your friend is more comfortable with plain HTML/CSS for MVP that works too — don't let frontend slow you down.

8. Data Freshness and Maintenance
8.1 Re-scraping Schedule
Every 48 hours, the scraper runs for all active sites. It compares product URLs against the existing hash registry and only re-processes products where the price has changed or the image URL has changed.
8.2 Dead Link Detection
A separate lightweight job runs every 24 hours that pings the image URLs of all stored products. Any product returning a non-200 response gets its is_active flag set to false and is excluded from search results. It is not deleted immediately — kept for 7 days in case it is a temporary outage.
8.3 Scraper Config Invalidation
If a scraping job returns zero products for a site three consecutive times, the system automatically flags that site's config as stale and triggers the Site Analyzer Agent to regenerate the scraping configuration for that site.

9. Infrastructure for MVP
Everything runs on a single cloud instance to keep costs near zero:
Single VM (AWS EC2 t3.medium or equivalent)
├── FastAPI backend process
├── APScheduler scraping jobs
├── CLIP model loaded in memory
└── SQLite for job tracking

Qdrant Cloud (free tier)
└── Vector storage and search

HuggingFace (free)
└── CLIP model weights
Total estimated monthly cost for MVP: under $20, possibly free if you use AWS/GCP student credits.

Build the Site Analyzer Agent and test it on one site
Build the Scraper Executor for that same one site
Connect scraper output to CLIP to Qdrant — end to end pipeline working
Build FastAPI search endpoints
Build the frontend
Test the full loop — scrape → embed → search → display
Add remaining sites one by one
Polish, document, deploy
